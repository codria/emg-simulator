# 筋電ロボットアーム展示 検討事項まとめ

オープンキャンパス展示用。左右腕のEMG 2chでロボットアームを操作する到達ゲーム。
本ドキュメントは実装着手前の設計判断と検討事項を集約したもの。

---

## 1. 全体構成

```
BioRadio (Bluetooth)
    ↓ .NET SDK (C# DLL)
pythonnet
    ↓
Python: 信号処理（整流→RMS→正規化→ソフト飽和）
    ↓ (r, θ)
Python: 逆運動学 + 3D描画 + ゲーム判定
```

**全面Python実装とする。** 既存C++資産はビルド可能だが、その方針を採らない理由は「2.5 実装方針」を参照。

### 担当スコープ

| 範囲 | 担当 |
|---|---|
| ロボットアーム実機・電極等の資材 | **スコープ外**（先方） |
| 信号取得〜処理〜(r,θ)出力 | 本プロジェクト |
| IK・3D描画・ゲーム判定 | 本プロジェクト（既存C++からロジックを移植） |

### 言語構成

- 書くのは **Python**（全レイヤー）
- **C#は書かない**。公式SDKの.NET DLLのメソッドを呼ぶだけ
- **C++は成果物に含めない**。既存資産からIKの数式とアームモデルのパラメータを移植する
- 土台は **Windows**

## 2. プラットフォーム制約（確定事項）

BioRadioは **Windows専用**。メーカー公式（GLNeuroTech）が以下を明言している。

- Windows 7以降以外のOSでの動作は設計されていない
- **BootCamp・VMWareもサポート対象外**
- SDK配布はWindows版のみ
- ホストPCに **Bluetooth 2.1以降** のアダプタが必要

→ Mac/Linuxでのライブ動作は不可。展示PCはWindows機で確定。

### Python連携の経路

公式のPythonバインディングは存在しない。3案のうち採用は1案目。

1. **pythonnet で .NET SDK を呼ぶ** ← 採用。公式に最も近い
2. LSL（Lab Streaming Layer）経由 — 中継アプリが必要
3. BioCaptureでファイル収録→オフライン処理 — ライブ不可のため今回は不採用

### 主要API

- デバイススキャン → MACアドレス取得 → 接続・設定
- `StartAcquisition()` で収録開始
- `GetScaledValueArray()` でスケール済み実値配列を取得
- データは **Signal groups** 単位で提供される（サンプルレート等の性質を共有する信号の集まり）

### 注意点

- SDKはファームウェア1.0で開発・テストされている。手元デバイスのFWをBioCaptureで確認すること
- 旧モデル（BioRadio 150等）はレガシー扱いで別サポート

## 2.5 実装方針：全面Python化（既存C++を流用しない理由）

### 前提

逆運動学・アームモデル・3D描画を含むC++資産が存在し、**開発機のVisual Studioからはビルド・実行できる**。
ただし **展示本番PCは別PC**であり、VSの設定が複合的に絡んだ状態のため、本番PCでの再構築には再設定が必要。

### 検討した3案

| 案 | 実行環境 | 評価 |
|---|---|---|
| A. 全面Python化 | Python + パッケージ + .NETランタイム | **採用** |
| B. pybind11でC++組み込み | Python + **C++ビルド環境（MSVC）** | 不採用 |
| C. C++を別プロセスで実行、(r,θ)をIPC送信 | C++実行ファイル + 依存DLL群 | 不採用 |

### A を採用した理由

1. **「開発機でビルドできる」は「本番PCで動く」を意味しない**
   現状はVS設定に依存しており、再現手順が明文化されていない。別PCでの再構築は依存ライブラリのパス・ランタイム・プラットフォームツールセット・構成の食い違いを個別に潰す作業になり、**所要時間が読めない**。締切のある展示案件で抱えるリスクが大きい。

2. **C案でも配布問題は残る**
   実行ファイルのコピーだけでは動かず、VC++再頒布可能パッケージ・依存DLL・描画ライブラリのランタイムが本番PCに必要。動作しなかった際、VSの無い本番PCでの原因切り分けが困難。C案の利点（ビルド巻き取り不要）が別PC配布という条件下でほぼ失われる。

3. **Python化なら環境が手順化できる**
   本番PCに必要なのは Python + パッケージ（`requirements.txt`）+ .NETランタイムのみ。再現性があり、展示前日のトラブル時も切り分けやすい。

### 移植の切り分け

**C++資産を全部移植するのではない。** 必要な部分だけ回収し、描画は今回必要な絵だけ新規に書く。

| 対象 | 方針 | 難度 |
|---|---|---|
| 逆運動学 | numpyへ移植。数式の塊なので機械的 | 低 |
| アームモデル（リンク長・関節制限） | パラメータを移し替えるだけ | 低 |
| 3D描画 | **移植せず新規実装**（PyQtGraph `GLViewWidget`） | 中 |

### 描画の実装見込み

描画対象は床・台座・アームリンク・目標球のみ。PyQtGraph（`pyqtgraph.opengl`）で足りる。

| 形状 | 実装 |
|---|---|
| 床 | `GLGridItem`、または平面メッシュ |
| 台座（立方体） | `MeshData.cube()` |
| 円柱 | `MeshData.cylinder()` |
| 円柱の側面蓋 | **PyQtGraphのcylinderは側面のみで蓋が付かない**。円盤の三角形扇を自前で追加するか、蓋なしで済ませる（リンク用途なら見た目の破綻はほぼ出ない） |
| 湾曲アーム | 元C++の生成方法による（下記） |

**湾曲アームの扱い** — 元のC++実装がどちらかで対応が変わる。

- パラメトリック生成（スイープ・押し出し等）→ 生成ロジックをPythonへ移植。numpyで頂点配列を作り `GLMeshItem` に渡す
- メッシュファイル（OBJ/STL等）読み込み → **ファイルをそのまま流用**し、trimesh等で読み込む（移植不要）

### 移植の検証方法

IK移植後、**既存C++と同一の目標座標を入力して関節角を突き合わせる**。
一致を確認できた時点で以降C++は不要になる。

## 3. 入力の割り当て設計

### 前提

EMG 2ch → 独立変数は2つ → **同時に独立制御できる自由度は最大2**。これは動かせない物理的制約。
ただし「2自由度をどの軸に割り当てるか」は自由であり、「2次元入力＝XY平面」は必然ではない。

### 採用：極座標への直接割り当て

| 入力 | 出力 | 体感 |
|---|---|---|
| 左腕 | **半径 r（リーチ）** | 左腕を力む＝前へ伸びる |
| 右腕 | **角度 θ（旋回）** | 右腕を力む＝旋回する |

脱力＝手元（待機位置）に戻る。左右どちらをどの軸に当てるかは実機で試して決めてよい。

### 採用理由

1. **到達領域と形が一致する**
   アームの可動範囲は扇形。極座標 `(r, θ)` はその形にそのまま貼れる。
   `r∈[r_min, r_max]`, `θ∈[θ_min, θ_max]` にクリップすれば **目標点が常に到達可能領域内に収まる**。
   デカルト直割り当てだと扇形の外に目標が飛んでIKが解なしになり、展示中に「動かない」事故が起きる。

2. **軸間の干渉が無い**
   左腕は半径のみ、右腕は角度のみに効く。**片方を操作しても、もう一方の軸は動かない**。
   これが後述の和差方式に対する決定的な優位点。

3. **左右の役割が明確に分かれる**
   二人協力モード（左右の電極を別々の人に装着）との相性が良い。
   「自分は向き担当」「自分は伸ばす担当」と役割が明確になり、因果が見えやすい。

### トレードオフ

身体マッピングの直感性は和差方式に劣る。「右腕＝向き、左腕＝伸び」は一度説明が必要。
ただし説明は一行で済み（係員が「右で向き、左で伸ばす」と言えば足りる）、
一度理解すれば干渉が無いぶん操作は素直。**この程度の説明コストは干渉解消の利益に見合う。**

### 不採用案（参考）

- **和差の極座標**（和 `左+右` → r、差 `左−右` → θ）
  「両腕で押す＝前に伸びる」「左右差＝向きが変わる」が説明不要で直感的、という利点はある。
  **ただし軸間干渉が致命的**。「右だけ少し強くしたい」と思って片腕を強めると和も増え、角度と同時に半径が動く。
  角度だけ変えたいのに前へ伸びてしまい、来場者には「思った方向に行かない」として体感される。
  一度は採用しかけたが、干渉の影響を評価して不採用に変更。

- **デカルト直交割り当て**（左→x、右→y）
  干渉は無いが、到達領域の角で解なしが出る（扇形にフィットしない）。
  非干渉の利点は上記の採用案が引き継いでいるため、こちらを採る理由が無い。

- **デカルト差動＋和**（和→前後、差→左右）: 扇形へのフィットが極座標に劣る上、干渉もある
- **モード切替**（2自由度をXY↔高さで切替）: 擬似3Dになるが同時制御ではない。今回は複雑さに見合わない

### 離散イベントの追加余地

連続制御は2つが上限だが、**閾値トリガで離散イベントは追加できる**。
（例: 両腕同時に全力＝何かの発動）実質2.5自由度。今回のゲームでは未使用だが拡張余地として。

## 3.5 操作難易度と制御方式（要検討）

### 問題

到達ゲームは「特定の座標に止める」課題であり、**EMGが最も苦手とする操作**を要求している。
理由は3つ。

1. 平滑化しても値は揺らぐ。「4割の力で保つ」が物理的に難しい
2. 力み続けると疲労で出力が落ちる。同じつもりでも値が下がる
3. 来場者は自分の筋出力を一定に保つ訓練をしていない

さらに到達判定に滞在時間（0.3〜0.5秒）を課しているため、まさに「止める」精度を試す設計になっている。
**難しくなるのは必然。** 対策なしでは展示として成立しない可能性がある。

### 対策の選択肢

難易度を下げる手段を、効果の大きい順に列挙する。

- **速度制御への変更（最も効果が大きい／要判断）**
  EMGを「位置」ではなく「速度」に割り当てる。力むほど速く動き、脱力で停止。
  位置制御は「特定の値を保つ」ことを要求するが、速度制御は「動かしたい時だけ力む、着いたら脱力」で済む。
  **脱力＝停止は誰でもできる**ため、止める難易度が劇的に下がる。

  トレードオフ:
  - 積分が入るため、**脱力してもドリフトする**リスクがある。5章のベースライン取得の重要度が上がる
  - 「脱力すると手元に戻る」という位置制御の分かりやすさは失われる

- **判定を甘くする（効果大・実装容易）**
  目標球の半径を大きく、滞在時間を短く。展示なら判定はかなり甘くてよい。

- **平滑化を強める**
  反応は鈍るが安定する。到達ゲームなら即応性より安定性を優先してよい。

- **スナップ（吸い付き）**
  目標に近づいたら軽く吸い寄せる。

### 判断待ち

**位置制御のまま判定を甘くするか、速度制御に変更するか。**
実機で両方試せるなら切り替え可能に実装するのが確実だが、労力は増える。
まずは位置制御＋甘い判定で実装し、操作感を見て速度制御を検討する段階的な進め方も可。

**注意：この判断は6章の目標マーカー表示と連動する。**
速度制御では入力値が位置に対応しないため、「この高さまで力めば着く」という関係が存在せず、
**バー上の目標線／目標帯が原理的に引けない**。目標マーカーを採るなら位置制御が前提になる。

## 4. ゲーム設計

### 形式：到達ゲーム（無限ループ型）

基部から **+y 側にオフセットした操作平面**に目標球を置き、極形式移動で目指す。
到達したら次の目標が湧く。

### +y オフセットの意味

見た目以上に効いている。操作平面を基部から前に離す＝ **`r_min > 0` を強制する**。
これにより **r≈0 の特異点**（半径ゼロだとθが不定になり、目標点がアーム根元に潜る）を構造的に踏めなくする。
脱力しても手前の待機ラインに戻るだけになる。

### 到達判定

- `‖先端 − 目標‖ < 閾値` が **連続0.3〜0.5秒** 成立で到達
- 瞬間通過での判定は不可。暴れた先端が偶然掠って当たりになるため
- 滞在時間を課すことで「狙って止める」操作になり、ゲームとして成立する
- ただし**この滞在要求が難易度の主因**でもある。展示では球半径を大きめ・滞在を短めに振ってよい（3.5節参照）

### 次目標の生成

- 到達領域（`r∈[r_min,r_max]`, `θ∈[θ_min,θ_max]`）内でランダム
- ただし **現在位置から一定距離以上離す**制約を入れる。近すぎる次目標は動かずにクリアされて間延びする

### ループの区切り

無限ループそのものは可。ただし展示では交代の区切りが必要。

- **「5個到達でタイム表示→リセット」** にしておくとタイムが自然にスコアになり、係員が「はい交代」と言いやすい
- 無限ループは **アトラクトモード**（誰も装着していない時のデモ放置画面）に回す

### 検討した他案（不採用）

- **UFOキャッチャー**: 形式としては2次元操作と噛み合い、インパクトも大きいが、シミュレータ規模が大きく労力面で見送り
- **筋電お絵描き・書道**: 軌跡が作品として残る利点があるが、今回は到達ゲームを優先

### 運用オプション

- **二人協力モード**: 左右の電極を別々の人に装着するだけ。**コード変更ゼロ**で当日のオプションとして使える。親子・友人同士との相性が良い

## 5. 正規化・キャリブレーション（最大の懸念点）

### 問題の構造

EMGの振幅は個人差が桁で違う。要因は皮下脂肪厚、電極位置、皮膚インピーダンス、その日の発汗。
同じ「全力」でも人により出る値が数倍違う。
生の振幅をそのまま使うと **非力な人はアームが動かず、体格のいい人は振り切れっぱなし**になる。

### 展示特有の落とし穴

標準的な対処はMVC正規化（開始時に両腕全力を数秒取得して割る）だが、展示では以下が起きる。

1. **全力を出してくれない** — 人前で力むのを恥ずかしがり、「全力」が実は5割。その後本気を出すと1.0を超えて振り切れる
2. **逆に張り切りすぎる** — 最大値取得直後に疲労で出力が落ち、後半動かなくなる
3. **時間がかかる** — 1人ずつ数秒の較正は、列ができると効いてくる

### 方針

**較正の精度を上げる方向ではなく、較正が雑でも壊れない設計にする方向。**
来場者相手に精密な較正は取れない前提で組む。

### 実装する合わせ技

- **ソフト飽和**
  較正値で割った後、1.0でクリップせず `tanh` 等で緩く飽和させる。
  較正が甘くても振り切れず、上を超えた分も緩く効く。

- **ベースライン（脱力時）取得**
  安静時のノイズフロアを引いてから割る。脱力しても値が乗るのを消せて「手を抜くと止まる」が効く。
  **全力より脱力の方が確実に取れる**ので、MVCより信頼できる。

- **オンライン適応**
  セッション中の観測最大値でスケールを緩く更新する。較正が5割だった人も、本気を出した瞬間に追従する。
  ただし **更新は上方向のみ・ゆっくり**。双方向・高速だと不安定になる。

- **フォールバック固定ゲイン**
  較正が失敗しても最低限動く既定値を持つ。**展示では「動かない」が最悪の事故**。

- **左右独立に正規化**
  利き腕の方が出やすい。左右まとめて正規化すると、脱力時も常に片側に寄る。
  MVC・ベースラインとも左右別々に取得すること。

## 5.5 画面表示：筋電位バー（採用）

### 配置

シミュレータ画面の**両サイドに現在の筋電位バーを表示する**。
画面左端に左腕、右端に右腕。身体との対応がそのまま画面配置になる。

### 採用理由

1. **操作のフィードバックとして機能する**
   EMGで狙った値に止めにくい一因は、**自分が今どれだけ力んでいるか見えない**こと。
   バーによる目視フィードバックがあれば「もう少し緩める」が可能になり、
   3.5節の難易度対策として判定緩和・平滑化と並ぶ効果がある。

2. **展示としての本体でもある**
   この展示の価値は「自分の筋肉が機械を動かす」因果の体感であり、バーはその中間項を可視化する。
   力む→バーが伸びる→アームが動く、の連鎖が見えることが学科展示としての説得力になる。
   並んでいる人・保護者にも操作者の状態が伝わり、待ち時間の見応えにもなる。

### 表示内容

- **メインのバー**: 正規化＋平滑化後の値（＝実際に制御に使っている値）。生波形はガタつきが大きくフィードバックに使えない
- **目盛り**: MVC較正後の 0〜1 を全高に割り当てる。ソフト飽和により1.0超の領域も少し見えるようにして「振り切れている」が分かるようにする
- **役割ラベル**: バー横に「伸び（r）」「向き（θ）」と表示。割り当ての説明を兼ね、係員の口頭説明を減らせる

### 生波形の併記（判断の余地あり）

メインはバー、補助として生波形を小さく併記する二段構えも可。
「筋電を計測している」ことが視覚的に伝わる利点があるが、必須ではない。

### 目標マーカー（判断の余地あり／位置制御が前提）

目標球の座標は生成時に決まっているため、**そこから逆算した入力値をバー上に表示できる**。

```
目標球 (r_t, θ_t)
  ↓ 入力→出力の写像を逆に辿る（正規化・ソフト飽和の逆関数を通す。tanhの逆はatanhで閉形式）
左腕バーの目標位置 = r_t を [r_min, r_max] で正規化した高さ
右腕バーの目標位置 = θ_t を [θ_min, θ_max] で正規化した高さ
```

**効果**: 「あとどれだけ力めばよいか」が直接見え、課題が「感覚で探る」から「マーカーに合わせる」に変わる。難易度が大きく下がる。

**副作用**: 課題の主対象が3D画面からバーへ移る。到達判定はアーム座標で行うため破綻はしないが、
**来場者がバーしか見なくなり、3D画面が飾りになる**可能性がある。

**制約**: 速度制御を採用する場合は原理的に実装できない（3.5節参照）。

#### 表示形式の選択肢

- **線** — 目標値をそのまま1本の線で
- **帯** — 目標球の半径に対応する幅を持たせる。「この帯に入れば当たり」が視覚的に分かり、判定の甘さも伝わる
- **遅延フェードイン** — 最初は出さず、数秒経っても届かなければ表示。自力探索の体験を残しつつ、詰まった人を救う

#### 3D画面側の対策

視線が完全にバーへ移るのを防ぐため、3D画面側にも手がかりを置く案がある。
目標球への距離リング、軌道表示など。

#### 検討時の観点

展示時間は1人あたり1分程度で、自力探索の時間はほとんど無い。
体験性（感覚を探る面白さ）と達成率（確実に成功させる）のどちらを優先するかで判断が分かれる。

## 6. 信号処理

### 前処理チェーン

```
生EMG → 帯域通過フィルタ → ノッチ（50/60Hz除去） → 整流 → RMS（窓処理） → 正規化 → ソフト飽和
```

- `numpy` / `scipy.signal` を使用
- ライブ処理のため **リングバッファ**に溜めながら窓ごとに処理
- 生EMGは激しく振動するため、整流→平滑化で「力の入れ具合」の連続値に均す。ここが安定しないとアームがガクつく

### RMS窓長（実測で決める）

- 短い → 反応が速いがガタつく
- 長い → 滑らかだが鈍い

**机上では決まらない。** 展示の操作感はここで決まる。
実機到着後に自分の腕で試し、**100ms〜300ms** の範囲で詰める。
RMS＋軽い指数移動平均の組み合わせで、安定と即応のバランスを取る。

## 7. スレッド構成

**取得・処理・描画を別スレッドに分ける。**

- SDKからの取得 → ワーカースレッド
- 描画 → GUIスレッド
- 間を **キュー**で繋ぐ

同一スレッドに全部置くと、取得のブロッキングでGUIが固まる。

---

## 8. モジュール構成

全レイヤーがPythonのインプロセス実装となるため、外部プロセスやFFIの境界は無い。

| 層 | 役割 |
|---|---|
| 取得 | pythonnet経由でBioRadio SDKから信号取得（ワーカースレッド） |
| 信号処理 | 帯域通過・ノッチ・整流・RMS・正規化・ソフト飽和 |
| 変換 | 左右の値 → 和・差 → `(r, θ)` → デカルト目標座標 |
| IK | 目標座標 → 関節角（C++から移植） |
| 描画 | PyQtGraph GLViewWidget（GUIスレッド） |
| ゲーム | 目標生成・到達判定・スコア |

層の間はプロセス境界を持たないため、以前検討していたpybind11やIPCによる接続は不要。
唯一のスレッド境界は「取得 ↔ その他」で、キューで繋ぐ（7章参照）。

### 既存C++から回収するもの

1. **IKの数式** — 関節角の解法。移植後にC++実装と数値を突き合わせて検証
2. **アームモデルのパラメータ** — リンク長・関節可動範囲・台座寸法
3. **湾曲アームの形状データ** — 生成ロジックかメッシュファイル（2.5節参照）

## 10. 実装の着手順

取得系（1〜4）と描画系（5〜7）は独立して進められる。実機が届く前でも描画系は着手可能。

1. **取得部の骨組み** — pythonnetでBioRadio SDKを叩き、値が取れることを確認（**最大の不確定要素**）
2. **波形モニタ** — 取れた信号をリアルタイム表示。処理チェーンの検証に使う
3. **正規化・キャリブレーション** — ベースライン→MVC→ソフト飽和→適応
4. **(r,θ) 変換** — 左腕→r、右腕→θ の直接割り当て、さらにデカルト目標座標へ

---

5. **IK移植** — C++の数式をnumpyへ。**C++実装と関節角を突き合わせて検証**（ここを通せば以降C++不要）
6. **描画** — PyQtGraph GLViewWidgetで床・台座・リンク・目標球。加えて両サイドの筋電位バー（5.5節）
7. **ゲーム層** — 目標生成・到達判定・スコア

---

8. **統合** — 取得系と描画系を接続、スレッド構成の確認
9. **本番PCでの動作確認** — `requirements.txt` から環境構築して再現性を検証

労力の重心は **1（取得部）と3（正規化）**。IK移植は機械的、ゲーム層は軽い。
描画は元C++からの移植ではなく新規実装だが、対象形状が単純なため中程度。
